4. JWT / SPRING SECURITY REVIEW
==================================================

JWT GENERATION:
✓ Uses JJWT library (io.jsonwebtoken)
✓ Secret key loaded from application.properties (app-jwt-secret)
✓ Secret decoded from BASE64 using Decoders.BASE64.decode()
✓ Uses HMAC-SHA256 signing via Keys.hmacShaKeyFor()
✓ Expiration: 604800000ms = 7 days ✓
✓ Claims include: subject (username), role, issuedAt, expiration
✓ Returns complete signed JWT token

ISSUE: Role claim uses getAuthorities().stream().findFirst()
- If user has multiple authorities, only first is included
- Spring Security UserDetails typically has one authority but this is fragile
- Better approach: include all authorities or use separate claim

---

JWT VALIDATION:
✓ Jwts.parser().verifyWith(key()).build().parseSignedClaims()
✓ Throws runtime exceptions for various JWT errors:
  - MalformedJwtException → "Invalid JWT token"
  - ExpiredJwtException → "Expired JWT token"
  - UnsupportedJwtException → "Unsupported JWT token"
  - IllegalArgumentException → "JWT claims string is empty"
  - Generic Exception → "Invalid Credentials"

ISSUE: All exceptions converted to generic RuntimeException
- Makes it hard to differentiate error types in filter/controller
- Response will be same for expired vs malformed vs invalid signature
- Better approach: Use specific exception types or return boolean

---

JWT FILTER EXECUTION:
1. JwtAuthenticationFilter extends OncePerRequestFilter (runs once per request)
2. Extracts token from Authorization header:
   - Gets "Authorization" header ✓
   - Checks if starts with "Bearer " ✓
   - Extracts token after "Bearer " (substring(7)) ✓
3. Checks Redis blacklist BEFORE validation ✓ (correct order)
   - If blacklisted: returns 401 with message ✓
4. Validates JWT signature and claims ✓
5. Loads UserDetails from username ✓
6. Creates UsernamePasswordAuthenticationToken with:
   - principal = UserDetails (object)
   - credentials = null (password not included)
   - authorities = UserDetails.getAuthorities() ✓
7. Sets authentication details (IP, etc.) ✓
8. Sets authentication in SecurityContext ✓
9. Calls filterChain.doFilter() to continue ✓

ISSUE: Exceptions in JWT validation are not caught
- JwtTokenProvider.validateToken() throws RuntimeException
- If validation throws, filter will pass (no setAuthentication)
- Authentication remains null for invalid tokens
- Then @PreAuthorize checks will fail with default message

FIX: Add try-catch in filter to handle validation exceptions gracefully

RATE LIMIT SERVICE:
RateLimitServiceImpl.isAllowed():
1. Redis increment key: Long count = redisTemplate.opsForValue().increment(key)
2. If count == 1 (first request in window):
   - Set TTL: redisTemplate.expire(key, Duration.ofSeconds(windowSeconds))
3. Return: count <= maxRequests

ISSUE: RACE CONDITION
Problem:
- increment() and expire() are two separate Redis calls
- Between increment (count=1) and expire() call:
  - Another thread/process might increment the key
  - But expire() still sets the TTL for the entire key
  - This is not a critical issue because both calls use same client
- However, there's a potential issue if Redis connection is lost
  - If expire() fails but increment() succeeded
  - Key never expires → rate limit is stuck for that user

RACE CONDITION IN TTL SETTING:
- If increment() returns 1 (first request), TTL is set
- But what if another request comes at the exact same millisecond?
- Both might see count=1, both try to set TTL
- This is unlikely to cause issues but is not perfectly atomic
- Better: Use Redis Lua script or use SETEX for atomic operation

VERDICT: MEDIUM SEVERITY - Works in practice but has theoretical race condition

BUG #4 - HIGH: Race Condition in Rate Limiting
API: Rate limiting for all endpoints
FILE: RateLimitServiceImpl.java
CLASS: RateLimitServiceImpl
METHOD: isAllowed()
LINE: ~15-17
SEVERITY: HIGH (potential)
PROBLEM: Redis increment and expire operations are not atomic
WHY IT IS A PROBLEM:
  increment() returns a Long count
  If count == 1, expire() is called in a separate Redis call
  Between increment and expire, other threads could increment the same key
  If expire() fails, key never expires and rate limit is stuck
STATIC FLOW:
  1. First request: increment(key) returns 1
  2. expire() called to set TTL = windowSeconds
  3. Another request at same millisecond: increment(key) returns 2
  4. Both requests see count <= maxRequests, both allowed
  5. If expire() fails between increment calls, subsequent requests accumulate forever
EXPECTED BEHAVIOR: Atomic increment + expire in single operation
CURRENT BEHAVIOR: Two separate Redis commands, not atomic
RECOMMENDED FIX:
  Use Redis Lua script for atomic increment and expire:
  local current = redis.call('INCR', key)
  if current == 1 then
    redis.call('EXPIRE', key, windowSeconds)
  end
  return current <= maxRequests
